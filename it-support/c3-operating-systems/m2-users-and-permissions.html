Users and Permissions

The essentials — hold these before the detail

The module at entry-certification level: what you must be able to do, and the facts the quizzes and drills on this page are testing. Read this first, every time.

You can — by the end of this module
  • create, modify and delete local users and groups on Windows and Linux
  • read a Linux permission string and change it with chmod and chown
  • explain least privilege and apply it to a real request
  • explain sudo and UAC, and why an admin should not live as root
  • set a password policy that is actually usable
Know this — the need-to-know core, 8 facts
Permission string
-rwxr-xr-- is type, then owner, group, other. r=4, w=2, x=1, so 755 means rwxr-xr-x.
Changing them
chmod takes symbolic (u+x) or numeric (755); chown changes the owner; chgrp changes the group.
Root and sudo
root (uid 0) can do anything. sudo runs one command with root rights and logs it, which is why it exists instead of logging in as root.
Windows
local users and groups (lusrmgr.msc) or `net user`; UAC elevates a single action rather than granting a permanent admin session.
Groups are the unit
grant rights to a group and put people in it. Per-person permissions become unauditable within a month.
Least privilege
the minimum access needed for the job, for the shortest time. Every extra right is a future incident.
Account lifecycle
create on day one, change rights when the role changes, disable the same day someone leaves, and settle the mailbox and files before deleting anything.
Password policy
length beats complexity, plus lockout thresholds and MFA. Forced 90-day rotation is no longer recommended by anyone serious.
The trap: chmod 777 to make something work. It works by deleting the control you were supposed to keep.

Everything below this box explains these lines, in this order, with a drill after each part that tests it. If you can say every line above without looking, the drills are revision. If you cannot, read the section that matches the line and come back — that is the whole study method. The same objectives for every module, built and not yet built, are on the learning path.

An account is a boundary

Who can do what is the whole of account administration, and half of security. Everything in this module is one of those two ideas.

The course splits users into two kinds, and the split is the point:

Standard userAdministrator
AccessAccess to the machine, with restrictions Complete control of the machine
CanUse the machine for its job. Cannot install software or change certain settings. View anyone's account, change and remove anyone on the computer, and view every single file
How manyAs many as there are people More than one is normal — and on a managed network, expected

Users who are categorised together by levels of access and permissions are put in groups. That sentence is the whole design: a group is a named bundle of rights, and people are put into it rather than being granted rights one at a time.

Least privilege

The A+ objectives call it the principle of least privilege: grant the minimum access a job needs, and no more. It is not a slogan — it is what decides every question in this module:

A new starter
A standard account. If the role needs admin, it gets a separate named administrator account — not membership of Administrators on their everyday login.
A shared folder
Group read and write, not Full Control. Full Control lets the user change the permissions, which is a different job from using the folder.
A request to "just make it work"
The permission that makes it work, at the narrowest scope that makes it work. Anything wider is a decision someone has to own.
The exam sentence: every right you grant is a future incident if it was not needed. Least privilege is the reason a compromised standard account is an inconvenience and a compromised administrator is an incident.

Windows: local users and groups

One console holds the accounts, the groups, the logs, the devices and the schedule. Knowing where the user management lives is most of this section.

The tool is Computer Management — search for it in the Start menu. If the top of the sidebar says Computer Management (Local), you are managing this machine only. A Windows domain is a network of computers, users and files added to a central database; an administrator in that domain can view those accounts and computers from any machine in it.

System Tools, corrected

The notes list these with their descriptions shifted down by one row. These are the correct pairings:

Handout correction: the notes' table pairs Task Scheduler with "where our system stores system logs", Event Viewer with "shared folders", and so on down the list — every description attached to the row above it. The table above is the correct pairing.

What you do in a user's properties

Reset a password
Right-click the user and change it, when they have forgotten it. They change it to their own at the next login.
Force a change
Tick User must change password at next logon. This is the right setting when you set the password and know it — and the right setting after a compromise.
Delete
Right-click, delete. It is immediate, and it is not reversible without recreating the account.

UAC: the prompt between a standard session and an administrator

User Account Control is the Windows feature that prevents unauthorised changes to a system. Its practical effect is that even an administrator's everyday session does not silently have administrator rights: a change that needs elevation raises a prompt, and you approve that change rather than running everything elevated.

That is the same idea as sudo on Linux, with a dialog box instead of a command — and the same reason behind it: an account that is always elevated turns every mistake and every piece of malware into a system-wide event.

Windows accounts from the shell

Five commands answer almost every account question you will be asked, and one of them is a question about group membership rather than users.

CommandWhat it tells you
Get-LocalUserThe local users. You will see your own account, the other real users, and a few default accounts that are part of Windows.
Get-LocalGroupThe local groups.
Get-LocalGroupMember AdministratorsWho is actually in a group. This is the command that answers "is he an admin?" with evidence.
net userThe classic view of local users, and the way you add, delete and set a password (next sections).
net localgroupThe classic view of local groups.

net is not PowerShell-specific: it is the old command-line tool for managing and configuring the operating system, and it still works. Both families are worth knowing because you will meet both — the cmdlet in a modern script, and net in a runbook written ten years ago.

The one habit to take from this section: check group membership before you believe a permission. "It says he is an administrator" is a claim; Get-LocalGroupMember Administrators is the answer. The same question on Linux is cat /etc/group.

There is also a direct console for this, which is the same window Computer Management opens: lusrmgr.msc. It is a shortcut, not a different tool.

Linux: root, sudo, and the file that guards them

There is exactly one superuser account. The interesting part is how you borrow its power for one line without becoming it.

Root is the first user created when a Linux system is installed, and it has all the privileges on the operating system: it is the superuser. Technically there is only one root account, but anyone who is granted access to use its powers can be called a superuser too — which is the difference between the account and the capability.

The proof: a file only root can read

/etc/sudoers is the file that says who may use sudo, and it is protected: an ordinary user reading it is refused.

Refused
cat /etc/sudoers — permission denied, because the file is readable by root only.
Allowed
sudo cat /etc/sudoers — the shell runs that one line as a superuser.

sudo, and su

sudo means "run this one command with superuser rights". It exists because being constantly logged in as root is dangerous: everything you type is a root command, including the typo.

su means substitute user. With no name after it, it switches to root. The usual form is sudo su -, and you can see it worked because the prompt changes from cindy@cindy-nyc:~$ to root@cindy-nyc:~#.

The # is a warning, not decoration. In that session, remove does not ask, permissions do not stop you, and the system directories are as writable as your home directory. Get out of it when the job is done — the course says so, and every runbook you will ever read says so.

What the user file holds

/etc/passwd holds user information. A line looks like root:x:0:0:root:/root:/bin/bash, and the first three fields are the ones to know:

FieldMeaningIn the example
1User nameroot
2Password — an x means the real one lives in /etc/shadowx
3User ID (UID). Zero is root.0

Groups on Linux, field by field

Four fields per line, and one of them explains a rule that sounds arbitrary until you see the file.

Membership lives in /etc/group. A line looks like sudo:x:27:cindy:

FieldNameMeaning
1Group namesudo
2Group passwordx — encrypted, and stored elsewhere. When a password is not specified for a group it defaults to the root password, which is why the field is normally an x and nobody touches it.
3Group ID (GID)27
4List of userscindy — the people in the group, comma separated when there is more than one.

Why this file is the answer to a permission question

Permissions on a Linux file are granted to the owner, the group, and everyone else. So when a file is readable by "the group", the only remaining question is who is in that group — and that is this file.

Add rights
Add the person to the group. Every file and directory that grants that group access is now open to them, in one change.
Remove rights
Take them out of the group. Every grant goes with them, and nothing is left behind pointing at a person who has left.
Audit
Read one file to answer "who can open this?" — instead of reading fifty individual grants and hoping you found them all.

This is the least-privilege argument in its practical form: rights belong to roles, people belong to roles, and the join between the two is short enough to check.

Windows passwords: set, reset, force a change

Three different jobs people call 'change the password', and the difference matters when someone has been compromised.

JobHow
The user changes itThey know the old one and change it themselves.
You reset itComputer Management → Local Users and Groups → the user → properties → set a new password. Tell them what it is; they change it at next login.
You force a changeTick User must change password at next logon. They cannot get to the desktop until they choose a new one.

The GUI sequence, from the notes:

  1. Open Computer Management.
  2. Go to the users list under Local Users and Groups.
  3. Choose the user who needs the change and open their properties.
  4. Tick User must change password at next login.
  5. At their next login they are forced to choose a new password.
  6. If they have forgotten it, right-click and set it manually — then they change it to their own at the next login.

From PowerShell: net user

CommandWhat it does
net user cindy some_passwordSets the password. It is now in your command history and possibly on someone's screen.
net user cindy *The better form: the shell pauses and asks for the password, so it never appears in the command line.
net user victor /logonpasswordchg:yesMarks the account so the person must change their password at the next logon.
Reset versus change is a security distinction, not a convenience one. If a password may have been seen by someone else — you set it, or it was compromised — then the account needs forced change at next logon, so the only person who knows the final password is its owner. Otherwise you have simply moved the shared secret from one person to two.

Linux passwords: passwd, and the shadow file

One command, two flags worth knowing, and the file the password is actually stored in.

CommandWhat it does
passwd cindyChanges cindy's password.
sudo passwd -e victorExpires victor's password, so the next login must set a new one. The Linux equivalent of "must change at next logon".

When you set a password it is scrambled and saved in /etc/shadow. That is why /etc/passwd shows an x in the password field: the readable file holds the account, the unreadable one holds the secret.

Why split them
/etc/passwd has to be readable by ordinary programs — they need to map a UID to a name. A scrambled password in a world-readable file is a file to take away and attack offline.
What "scrambled" means
It is a hash: a one-way transformation. Nothing recovers the password from it; a login is checked by hashing what you typed and comparing.
The support rule
Nobody can tell a user their password. A forgotten one is reset, not recovered — the same rule on both systems.

Note the pattern across the two systems, because it is the one thing worth carrying out of this section: Windows has a checkbox for "change at next logon" and a /logonpasswordchg:yes flag; Linux has passwd -e. Different words, same control.

Adding and removing users

Four jobs on Windows, two on Linux, and one habit: never leave a new account with a password only you know.

JobWindowsLinux
Add a user, prompted for the password net user andrea * /add sudo useradd juan
Force a change at first login net user andrea /logonpasswordchg:yes sudo passwd -e juan
Add with the password in one command net user cesar pa5sw0rd /add /logonpasswordchg:yes —
Delete a user net user andrea /del or Remove-LocalUser cesar sudo userdel juan

Two details that catch people out:

The asterisk
net user andrea * makes the shell prompt for the password instead of taking it as an argument. Use it every time: a password in a command line is a password in the history file.
The password step
useradd creates the account; setting the temporary password is a separate passwd step, and -e is what expires it.
sudo
Both Linux commands need it. Creating or deleting an account is a root action, and the shell will refuse without the prefix.
Remember to let the user change their password. The notes say it twice, which is the right number of times: an account created with a password the technician chose and never forced to change is an account with a shared credential. Add the user, force the change, hand over.

The handout's cheat sheet also lists sudo deluser <user> for Linux. It is the same job as userdel and it is the Debian spelling; use whichever the machine's documentation uses, and know that both exist.

The account lifecycle

Adding and deleting are the two ends of a longer process, and the middle is where most permission problems live:

Create
Least privilege from the first minute: a standard account, in the groups the role needs, with a forced password change.
Change of role
The rights change with the role, in both directions. Rights granted for a project that ended are the ones nobody remembers to remove.
Departure
Disable or expire the account before deleting it, so anything still logging in as that person fails visibly rather than silently continuing.

The A+ objectives supply the same controls under "account management": restrict user permissions, restrict log-in times, disable the guest account, use failed-attempt lockout, use a timeout or screen lock, and apply account expiration dates. Each one is a lever against the same risk — an account that keeps working after it should have stopped.

Password policy that people can actually live with

A policy that produces sticky notes on monitors has failed, whatever it says on paper.

The A+ objectives list five password considerations: length, character types, uniqueness, complexity and expiration. They are not equal in value, and the order above is close to how much each one buys you.

LeverWhat it doesThe trade
LengthEvery extra character multiplies the guessing work. This is the cheapest strength there is.Long and simple beats short and cryptic — and people can remember a passphrase.
UniquenessA different password per service, so one breach does not become five.Nobody does this without a password manager, which is why the A+ list also includes using one.
Complexity and character typesRules about uppercase, digits and symbols, intended to defeat guessing.Pushed too far they produce P@ssw0rd1, which satisfies the rule and defeats nothing.
ExpirationForces a change on a schedule.A forced change on a fixed short cycle produces predictable increments — and a note on the monitor.

The controls that do the most work sit outside the password itself, and the A+ list has them under account management:

Failed-attempt lockout
The account locks after a set number of wrong tries, which makes guessing through a login prompt impractical.
Multifactor authentication (MFA)
A password plus something else — a code, a token, an authenticator app, a hardware key. A stolen password alone stops being enough.
Screen lock and timeout
An unattended, unlocked session is a password that has already been typed for you.
Account expiration
A date after which the account stops working: the control that covers a contractor, a term of study, or a forgotten service account.
This module's own line, stated plainly: length beats complexity, and forced 90-day rotation is no longer recommended by anyone serious. Build the policy from length, uniqueness, a second factor and lockout — those are the four levers that change the outcome.

The five considerations and the account-management list are quoted from the CompTIA A+ Core 2 objectives — "configure and apply basic Microsoft Windows OS security settings" and "apply workstation security options and hardening techniques". The notes cover setting and expiring a password but not policy, so the policy framing is the A+ overlay, not the handout.

Windows permissions are ACLs

A list attached to each file, naming who may do what. The letters on the end of an icacls line are that list in shorthand.

Windows assigns file and folder permissions with access control lists (ACLs). The one that decides who may do what is the Discretionary ACL (DACL). There is a second kind: a System ACL (SACL) tells Windows to write an event-log entry every time someone accesses that file or folder — auditing rather than permission.

The six permissions

PermissionWhat it allows
ReadSee that the file exists and read its contents. On a directory, read the files and directories inside it.
Read & ExecuteRead, and run the file if it is executable. It includes Read — tick this and Read is ticked with it.
List folder contentsAn alias for Read & Execute on a directory: tick one and the other ticks. It means you can read and execute the files in that directory.
WriteMake changes to a file — and, surprisingly, you can have Write on a file without Read. On a directory it means create subdirectories and write files into it.
ModifyAn umbrella: Read, Execute and Write together.
Full ControlEverything Modify allows, plus taking ownership of the file and changing its ACL.
Full Control is a different job from using the file. It lets the user change who else has access — which is why a home folder grant is Modify, not Full Control. Handing out Full Control is how a permission problem becomes a permission problem you cannot see.

Reading and changing them: icacls

icacls (improved change ACLs) is the command-line view. Run it on a folder and it prints one entry per account, in one compact form:

The entry
CINDY-NYC\cindy:(OI)(CI)(F)
CINDY-NYC\cindy
The machine (or domain), then the account.
(OI)(CI)
Inheritance: the entry applies to files and folders created inside this one, not only to the folder itself. Object inherit (OI) is the file half, container inherit (CI) the folder half.
(F)
Full control. The letters are the shorthand: F full control, M modify, RX read and execute, R read.

icacls /? prints the full legend, which is the same "read the help rather than memorise it" rule as every other command in this course.

CommandEffect
icacls "C:\Vacation Pictures" /grant "Everyone:(OI)(CI)(R)" Give everyone read access, inherited to the files and folders inside.
icacls "C:\Vacation Pictures" /grant "Authenticated Users:(OI)(CI)(R)" The tighter version: only accounts that log in with a password, not the guest.
icacls "C:\Vacation Pictures" /remove Everyone Take that entry away again.
icacls file.txt /reset Drop the explicit entries and go back to what the parent folder grants.

In PowerShell the parameters need quoting around the account and permission pair; in cmd.exe they do not. That is a shell difference, not a permissions one.

Guest is worth one line: it is a special account that can use the computer without a password, disabled by default, and enabling it re-opens exactly the door that "Authenticated Users" was written to close.

Reading a Linux permission string

Ten characters. The first one is not a permission at all, and the other nine are three groups of three.

ls -l ~/my_file prints a line whose first field looks like -rwxrw-r--. That is ten bits, and it decodes like this:

BitMeaningIn -rwxrw-r--
1File type, not a permission. - is a regular file; d is a directory.-
2, 3, 4The owner's permissionsrwx
5, 6, 7The permissions of the group the file belongs to rw-
8, 9, 10The permissions of everyone elser--

Inside each triple, the order never changes and the letters never change:

r
Readable — read the contents of a file, or list a directory.
w
Writable — write information to the file or folder.
x
Executable — run the program. On a directory, this is what lets you enter it and reach what is inside.
-
Disabled: that permission is off.

So -rwxrw-r-- reads as: a regular file; the owner can read, write and execute it; the group can read and write; everyone else can only read.

The x bit on a directory is the one that trips people up. A permission is only proven by the account that needs it, and a "permission denied" is often not the file at all — it is a missing execute bit on one of the directories leading to it. namei -l is the tool for exactly that: it prints every directory on the path, so the missing bit shows up where it actually is.

The eight digits, all of them

Four, two and one. Once you can turn a digit into three letters without thinking, chmod stops being a code.

Each permission triple is a three-digit binary number, and binary converts to one octal digit. Read is 4, write is 2, execute is 1, and you add the ones that are switched on. That is the whole system — the table below is those eight sums, which is the part the notes leave to one example.

Octal digitBinary (r w x)Math (4 + 2 + 1)SymbolicMeaning
00 0 00 + 0 + 0 ---No permissions
10 0 10 + 0 + 1 --xExecute only
20 1 00 + 2 + 0 -w-Write only
30 1 10 + 2 + 1 -wxWrite and execute
41 0 04 + 0 + 0 r--Read only
51 0 14 + 0 + 1 r-xRead and execute
61 1 04 + 2 + 0 rw-Read and write
71 1 14 + 2 + 1 rwxRead, write, and execute

Turning a three-digit number into a permission string

Read the digits in order — owner, group, other — and translate each one through the table above:

NumberOwnerGroupOtherSymbolic
7557 = rwx5 = r-x5 = r-x rwxr-xr-x
7537 = rwx5 = r-x3 = -wx rwxr-x-wx
6406 = rw-4 = r--0 = --- rw-r-----
4324 = r--3 = -wx2 = -w- r---wx-w-
Work it in both directions until it is automatic. Given rwxr-x---, the digits are 750: read the triple, add the weights, write the digit. That is the quiz, and it is the interview question.

Changing permissions: chmod, chown, chgrp

Two ways to write the same change — symbolic and numeric — and two other commands that change who the permissions apply to.

Symbolic: who, what

chmod takes a who, an operator, and a permission:

Who
u owner, g group, o other, a all three.
Operator
+ add, - remove, = set exactly.
Permission
r, w, x — and they can be combined after the operator.
CommandEffect
chmod u+x my_cool_fileGive the owner execute. Nothing else changes.
chmod u+rx my_cool_fileGive the owner read and execute in one go.
chmod g-w my_cool_fileTake write away from the group.
chmod 753 my_cool_fileThe numeric form: exactly 753, whatever it was before.

The distinction worth holding: + and - are relative — they change one thing and leave the rest — while a number is absolute — it sets all nine bits at once.

chown and chgrp: who the permissions belong to

Changing the bits does nothing if the wrong person owns the file. Two commands fix that:

chown
sudo chown devan my_cool_file — the owner becomes devan.
chgrp
sudo chgrp best_group_ever my_cool_file — the group becomes best_group_ever.

Both need root, because handing ownership to someone else is exactly the power a standard user must not have.

Two worked fixes

ModeMeansWhen it is the answer
600Owner read and write, nobody else anything Private data: a secrets file, a private key, a working document.
640Owner read and write, group read, others nothing A file the team must read and only the owner should change. With the right group this is the least that works.
The trap this module is named for: chmod 777 to make something work. It does make it work — by deleting the control you were supposed to keep. If the file is meant to be readable by the group, the answer is 640 with the right group, not 777 with no group at all.

And test as the account that needs it, not as root. A permission is only proven by the identity that has to use it — which is why you read the mode back, then try the operation as a user who is not the owner.

SetUID, SetGID and the sticky bit

Three bits that sit in front of the nine, and each one changes what running the file means.

All three are written as a fourth digit in front of the usual three, and each shows up as a letter where a permission letter would be.

BitOctalShows asWhat it does
SetUID4s in place of the owner's x The file runs with the permissions of the file's owner, not of the person who ran it.
SetGID2s in place of the group's x The group version of the same idea: it runs as the file's group. On a directory, new files inherit that group.
Sticky bit1t at the end On a directory: people can write to it but cannot delete things that are not theirs.

So the numbers the notes give are the ordinary number with the special bit in front:

SetUID
753 becomes 4753.
SetGID
753 becomes 2753.
Sticky
753 becomes 1753.

Why SetUID is the one that deserves respect

If a root-owned program has SetUID set, then anyone who runs it is running code with root's permissions. That is sometimes the point — some system tools have to act for an ordinary user — and it is also why an unexpected SetUID file deserves an explanation: a flaw in that program is a flaw that runs as root for anyone who can run it.

The habit: when a file shows an s where you expected an x, stop and ask whose permissions it runs with. Most files never need it, so an unexpected one is worth explaining before it is worth trusting.

SetGID on a directory, concretely

This is the one you will actually use. A project share on a Linux server takes two commands:

CommandWhat it sets
sudo chown alice:project /srv/shares/project/alice Owner alice, group project.
sudo chmod 2770 /srv/shares/project/alice SetGID, plus read/write/execute for the owner and the group, nothing for anyone else.

2770 is SetGID plus group read and write, with nothing for anyone else. The 2 is what makes new files inherit the project group instead of the creator's own primary group — which is the difference between a share where everybody can read everybody's files and one where the first person to save a document owns it alone.

The sticky bit is the same idea for deletion. On a shared directory it lets everyone write their own files while stopping them deleting anyone else's — the classic case being the temporary directory every Linux system has, where the world can write and nobody can tidy up someone else's work.
