Know this — the need-to-know core, 10 facts

Port ranges
0-1023 well known, 1024-49151 registered, 49152-65535 ephemeral (the source port your machine picks).
Socket
IP address + port + protocol. A connection is a pair of sockets, which is how one server serves thousands of clients on one port.
TCP handshake
SYN, SYN/ACK, ACK - three messages. Close is FIN, ACK, FIN, ACK - four.
Sequence numbers
they count bytes, not packets, which is how a lost segment is retransmitted precisely instead of resending everything.
UDP
no connection, no ordering, no retransmission. Cheap and fast: DNS queries, DHCP, voice, video, games.
HTTP
request and response. Methods GET/POST/PUT/DELETE. Status codes: 2xx success, 3xx redirect, 4xx your fault, 5xx their fault. HTTPS is HTTP inside TLS.
DNS
resolves a name to an address over UDP 53. Records worth knowing: A, AAAA, CNAME, MX, NS, TXT.
Mail
SMTP sends (25, or 587 for submission), POP3 downloads and usually removes (110), IMAP syncs and leaves it on the server (143).
Firewalls
stateless filters each packet by rule; stateful remembers connections and allows the replies. Default deny is the only sane posture.
The trap: Mixing up the handshake and the close. The handshake is three messages, the close is four, and swapping them is the single most common lost mark in this module.

What the transport layer is for

The network layer delivers to a machine. The transport layer delivers to a program — and decides how much it cares about reliability.

Module 2 ended with a packet that knows which machine it belongs to. That is not enough: a machine runs dozens of programs that all want network traffic, and something has to know which arriving data belongs to which one.

JobWhat it means
MultiplexingMany programs share one network connection. The transport layer keeps their traffic apart using port numbers.
SegmentationSplit a large message into pieces small enough to travel, and put them back together in the right order at the other end.
ReliabilityDecide whether lost or out-of-order pieces are detected and resent (TCP), or ignored (UDP).
Flow controlStop a fast sender from drowning a slow receiver.
The whole module in one sentence: TCP and UDP are the two ways to do those four jobs, and almost every networking question at this level comes down to which one a given application chose, and why.

Above them sits the application layer — HTTP, DNS, SMTP — which is the part users actually name. The transport layer is the plumbing that makes those protocols possible without each of them reinventing retransmission.

Ports: how one machine runs many conversations

A port is a number that identifies a program, the way an apartment number identifies a door in a building.

An IP address gets data to the machine. A port number gets it to the program. Together they form a socket: 192.168.1.10:443 is a specific program on a specific machine.

RangeNameUsed for
0 – 1023Well-knownThe famous services. Binding one usually requires administrator rights, precisely so an ordinary program cannot impersonate a server.
1024 – 49151RegisteredSoftware that wants a predictable port: databases, game servers, vendor services.
49152 – 65535Ephemeral (dynamic)What your machine picks as the source port for an outgoing connection. Temporary, and reused after the connection closes.

Why the pairing matters: a connection is identified by four values — source address, source port, destination address, destination port. That is how your browser can open six connections to the same web server at once: same destination, six different source ports.

TCP: the three-way handshake and numbered bytes

TCP's guarantee is built from sequence numbers, acknowledgements and a conversation that starts with three messages.

The header fields that matter

FieldWhat it does
Source / destination portWhich program on each end.
Sequence numberWhich byte of the stream this segment starts at. This is what makes reassembly and retransmission possible.
Acknowledgement numberThe next byte the sender expects — so "I have everything up to here".
FlagsSYN (start), ACK (acknowledging), FIN (finished), RST (reset — abort), PSH, URG.
Window sizeHow much data the receiver can still accept. This is flow control: a slow receiver shrinks the window and the sender slows down.
ChecksumDetects corruption in transit.

The handshake

1. SYN
Client: "I would like to talk, and my numbering starts at X."
2. SYN-ACK
Server: "I heard you, I have X+1. My numbering starts at Y."
3. ACK
Client: "I have Y+1. We are open."

Three messages, because three is the minimum that proves both directions work. After SYN the client knows it can send; after SYN-ACK it knows the server can send and can hear; the final ACK proves the client heard the server. Two messages would leave one direction unproven.

Closing, and why it takes four messages

TCP is full duplex, so each direction closes separately: FIN from one side, ACK, then FIN from the other and a final ACK. The side that closes first then waits in TIME_WAIT — typically two minutes, twice the maximum time a packet can survive on the network — so that a delayed duplicate cannot be mistaken for the start of a new connection.

RST is the abort: "this connection does not exist, stop talking". A port scan produces RSTs, a firewall that rejects rather than drops produces RSTs, and a service crash often leaves clients receiving them. A reset is information, not a fault in itself.

TCP socket states, and what they tell you

Every connection is a state machine, and the state is readable evidence when something will not connect — or will not let go.

StateMeaningWhen you see it and it is a problem
LISTENA server is waiting for connections on that port.Absent when it should be present: the service is not running, or is bound to a different address.
SYN_SENTYou sent SYN, no answer yet.Stuck here means the packets are being dropped — firewall, wrong address, or nothing listening.
SYN_RECEIVEDServer replied to a SYN, waiting for the final ACK.A flood of these is a SYN flood: half-open connections exhausting the backlog.
ESTABLISHEDThe conversation is open.Established but no data moving points at the application, not the network.
FIN_WAIT / CLOSE_WAITOne side has closed and the other has not finished.Thousands of CLOSE_WAIT means the application is not closing its sockets — an application bug, and eventually an exhausted port table.
TIME_WAITClosed, holding the port briefly so late packets cannot be confused with a new connection.Normal. A very large number means many short connections, which is a design question, not a fault.

On this machine you read them with ss -tan (or netstat -ano on Windows). The habit worth building: check the state before you change anything. "Nothing is listening on 443" and "443 is established but the page never loads" are two completely different tickets.

UDP: send it and forget it

No handshake, no acknowledgements, no ordering. Sometimes that is exactly right.

UDP wraps application data in a datagram with a source port, a destination port, a length and a checksum. That is the whole header — eight bytes, against TCP's twenty or more. It does not connect, does not acknowledge, does not retransmit and does not reorder.

Why it exists
A retransmitted packet that arrives 300 ms late is worse than useless in a voice call: you cannot un-play the silence. Better to lose it and carry on.
Who does the work
The application, if it cares. DNS retries a query that gets no answer. QUIC (HTTP/3) rebuilds reliability on top of UDP, in userspace, where it can be improved without changing every operating system.
Broadcast and multicast
Only UDP can do them — DHCP discovery is a broadcast, which is why DHCP is UDP.
The catch
No congestion control by default, so a badly written UDP application can starve everything else on the link.
TCPUDP
ConnectionThree-way handshakeNone
DeliveryOrdered, acknowledged, retransmittedBest effort
SpeedSlower to start, faster on a clean link thanks to windowingNo setup cost at all
Header20+ bytes8 bytes
Used byHTTP/1.1 and 2, SSH, SMTP, IMAP, SMB, FTPDNS, DHCP, SNMP, NTP, VoIP, games, streaming, HTTP/3
The exam version: TCP when every byte must arrive; UDP when late data is worthless or when one message goes to many receivers. If a question asks why a protocol chose UDP, the answer is almost always "because a late packet is worse than a lost one" or "because it has to broadcast".

Firewalls, in the transport layer's terms

A firewall is a rule about which sockets may exist. Everything else is detail.

A firewall inspects packets and decides whether to let them through. At this layer the decision is usually about five things: source address, destination address, protocol, port, and connection state.

StatelessStateful
Decides byEach packet on its own, against a fixed list of rules.The packet and the connection it belongs to.
Allows replies?Only if you wrote a rule for them too — the classic mistake is allowing outbound 80 and then wondering why nothing comes back.Yes: once a connection is established, return traffic is recognised and permitted automatically.
SeesAddresses, ports, flags.All of that plus the TCP state — SYN, ESTABLISHED, related.
Rule order
Most firewalls evaluate top to bottom and stop at the first match. One permissive rule above a restrictive one makes the restrictive one invisible.
Default deny
The only defensible default: block everything, then open what a service actually needs. The opposite means you are trusting everything you forgot to block.
Ingress vs egress
Incoming is what everyone thinks of. Outgoing matters too: it is how malware phones home and how data leaves.
DMZ
A segment for services that must be reachable from outside, kept separate so that compromising one does not put it next to everything else.
The support question that decides everything: "which port, from where, to what?" A ticket that says "open the firewall for the app" is not actionable. A ticket that says "allow TCP 8080 from the 10.20.0.0/24 subnet to 10.20.5.14" is a rule somebody can implement and later remove.

The application layer: the protocols users actually name

HTTP, DNS and mail. Above the transport layer, and the layer where most of the tickets people describe as the internet being broken actually live.

HTTP and HTTPS

HTTP is a request and a response: a method, a path, headers, and optionally a body.

GET
Fetch something. Should have no side effects.
POST
Send data that changes something — a form, an upload, a login.
PUT / PATCH / DELETE
Replace, partially update, remove. The verbs of an API.
HEAD
Headers only: is it there, and how big is it.
StatusMeansWho is at fault
200OKNobody.
301 / 302Moved permanently / temporarilyNobody: follow the redirect.
400Bad requestThe client sent something malformed.
401 / 403Not authenticated / not authorised401 means "who are you", 403 means "I know who you are and no".
404Not foundThe path does not exist — a client or content problem.
500Server errorThe server. This is the one to escalate.
502 / 504Bad gateway / gateway timeoutSomething between you and the application — a proxy or load balancer that cannot reach what is behind it.

HTTPS is the same protocol inside TLS: the connection is encrypted, and the server proves its identity with a certificate signed by an authority your machine already trusts. Port 443.

DNS, briefly

DNS turns names into addresses. A lookup walks a hierarchy — root, then the top-level domain, then the authoritative server for that domain — with caching at every step to keep the load sane. It runs on port 53, UDP for normal queries and TCP for answers too large for a datagram.

Mail

ProtocolPortJob
SMTP25 (587 for submission)Sending, and relaying between servers.
POP3110 (995 secure)Download and typically delete. One device.
IMAP143 (993 secure)Keep on the server and sync state. Many devices.

The distinction that matters in support: "my mail is not sending" is SMTP; "my mail is not arriving in my inbox" is IMAP or POP3. They are different servers, often different companies, and always different tickets.

One packet, four layers, end to end

The recap that makes the whole course one object instead of six chapters.

You type https://example.com and press Enter. Here is what actually happens, layer by layer, with the module that taught each row.

LayerWhat it addsIn this example
ApplicationThe request itselfGET / HTTP/1.1 plus headers — Module 3
TransportPorts, sequence numbers, reliabilitySource port 51234 → destination 443, TCP, SYN first — Module 3
NetworkAddresses and routingYour IP → the server's IP, TTL decrementing at each hop — Module 2
LinkFrames and physical addressingEthernet frame to your router's MAC, then the next hop's, and so on — Module 1

Each layer wraps the one above it — encapsulation — and the receiver unwraps in reverse. Nothing above the link layer knows what medium the data crossed; nothing below the application layer knows what the bytes mean.

This table is a diagnostic tool. Ask which layer the symptom is in, and half the possibilities disappear at once: a name that will not resolve is DNS (application), a connection refused is transport, a machine that cannot be reached at all is network, and a cable that is not lit is link.
