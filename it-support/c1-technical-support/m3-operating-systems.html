The essentials — hold these before the detail

The module at entry-certification level: what you must be able to do, and the facts the quizzes and drills on this page are testing. Read this first, every time.

You can — by the end of this module
  • explain kernel versus user space, and why the split exists
  • describe what a filesystem does and name the common ones per operating system
  • explain process and memory management, including virtual memory
  • read a boot sequence and say what has failed at each stage
  • choose between Windows, Linux, macOS and ChromeOS for a given need
  • explain what a virtual machine is, and when to use one
Know this — the need-to-know core, 8 facts
Kernel
the privileged core that talks to hardware, schedules processes and enforces permissions. Everything else, including your apps, is user space.
Filesystem
organises a disk into files and directories. NTFS on Windows, ext4 on Linux, APFS on macOS, exFAT/FAT32 for removable media.
Process
a running program with its own memory and an ID. The scheduler decides which process runs on which core, and for how long.
Virtual memory
each process gets its own address space, and pages move to disk when RAM runs out. Constant paging is the 'why is it so slow' slowdown.
Boot chain
firmware (UEFI) finds the bootloader, the bootloader starts the kernel, the kernel starts init/systemd, then you log in. Knowing the order tells you which log to read.
Logs
Event Viewer on Windows; /var/log and journalctl on Linux. The first place to look, before changing anything.
Virtual machine
a whole operating system running on virtual hardware. Cheap isolation and snapshots are why test machines are disposable.
Mobile OS
iOS and Android. Apps are sandboxed, updates come through a store, and permissions are granted per app rather than per user.
The trap: Treating 'out of memory' and 'disk full' as the same fault. They produce similar symptoms - an app crashes - and completely different fixes.

What an operating system actually does

Five jobs. If you can name them, every other section of this module has somewhere to sit.

JobWhat it decidesWhy an application must not do it itself
Process managementWhich program runs, for how long, and on which core.Two programs both deciding they own the CPU is a crashed machine.
Memory managementWhich process gets which memory, and what happens when there is not enough.One program writing into another's memory is how crashes and exploits happen.
File managementHow data becomes files and folders in a filesystem.Every program inventing its own storage layout would be chaos.
I/O managementTalking to devices through drivers, and handling interrupts.Applications would each need to know how every printer, disk and keyboard works.
The interfaceWhat you see and type: GUI, shell, and settings.Not a correctness issue — a usability one, and the reason the rest exists.
The definition to hold: the operating system is the layer that manages the computer's resources and lets a human and their programs use them, without any of them having to know how the hardware works. It is the second of the four layers from Module 1 — the one standing between hardware and software.

This is also why troubleshooting starts with "which layer?". An application that closes when you click Print is not necessarily a broken application: it could be the driver, the spooler, the filesystem it cannot write to, or the printer. The operating system is where those layers meet, which is why so many tickets end up here.

Kernel space and user space

The single most important division in an operating system, and the reason a bad application does not take the machine with it.

Kernel spaceUser space
What runs thereThe kernel: scheduler, memory manager, filesystem drivers, device driversEvery application, the desktop, the shell, your browser
AccessFull: it can touch any memory and any deviceRestricted: it can only touch its own memory
If it goes wrongKernel panic, blue screen, the whole machine stopsThe application closes, and nothing else notices

An application cannot open a file by itself. It asks the kernel, through a system call — open, read, write, exit. The CPU switches into kernel mode, does the work, and switches back. That boundary is why malware tries so hard to get into the kernel, and why a driver bug is more dangerous than an application bug.

Ways to talk to the machine

GUI
Graphical user interface — windows, icons, pointer. Discoverable, and slow to do anything twice.
CLI
Command-line interface — a prompt where you type. Not harder, just less forgiving of not knowing the command.
Shell
The program that reads what you typed and asks the kernel to do it. bash is the common Linux shell; PowerShell and cmd on Windows; zsh by default on macOS.
Why support work ends up in the shell: a shell command is repeatable, scriptable, and gives you the actual error. "It says no" from a dialog box has no information in it; Permission denied (os error 13) tells you exactly what to fix.

Processes: taking turns, convincingly

One CPU can appear to run fifty programs at once. The trick is a queue and a very short turn.

A process is a running program: its code, its memory, its open files, and its state. The kernel's scheduler gives each one a time slice — a few milliseconds — then saves its state and switches to the next. Switching is fast enough that the result looks simultaneous. On a multi-core machine several really do run at once, but the illusion still does most of the work.

StateMeaning
RunningHas the CPU right now.
ReadyWants the CPU, waiting its turn in the queue.
Waiting / blockedWaiting for something else: a disk read, a network reply, a key press. Consumes no CPU while it waits.
TerminatedFinished, or killed. Its memory is released.

What this explains in real life

"Not responding"
The window is in the waiting state and its message queue is not being drained — often because it is blocked on something that will never arrive.
100% CPU
One process is never blocking. Find it before you reinstall anything: Task Manager, Activity Monitor, or top.
Priority
The scheduler can be told that one process matters more. That is what "high priority" means, and why setting everything to high achieves nothing.
Zombie process
Finished, but its parent has not collected the exit status. Harmless, and a sign of a buggy parent.

Memory management and virtual memory

Every process believes it has the memory to itself. It does not, and that lie is the feature.

Each process gets its own virtual address space. The hardware and the kernel translate those virtual addresses into real physical ones, page by page. Three things fall out of that:

  • Isolation. A process cannot read another process's memory, because its addresses simply do not map there.
  • No address collisions. Two programs can both use the address 0x1000 happily.
  • Virtual memory. Pages not being used can be moved out to disk and brought back on demand, so a program can be given more memory than is physically installed.

Pages, swapping, and thrashing

Memory is divided into pages, typically 4 KB, and moved in those units. When physical RAM is full, the kernel writes the least recently used pages to a swap file or partition and frees them. When they are needed again, it reads them back — from a disk that is thousands of times slower than RAM.

Thrashing is what happens when there is not enough RAM for the working set: the machine spends nearly all its time swapping pages in and out and almost none doing work. The symptom is a machine that is "slow" but has low CPU usage and constant disk activity. The fix is more RAM, or fewer things open — not a faster CPU.

Modern systems also compress memory instead of swapping it, which is faster than disk and slower than doing nothing. And they will kill a process to stay alive — the Linux OOM killer, or macOS refusing to launch an application. That is not instability; it is the memory manager making a choice.

Files, folders and filesystems

A filesystem is the operating system's promise about how data is found, named and protected.

A file is a named block of data; a folder (directory) is a container of names. The filesystem is the structure that maps names to blocks on the device — and it decides what metadata exists, what permissions mean, and how big a file can be.

Blocks, not streams

Data is written in fixed-size blocks (commonly 4 KB). A 1-byte file still consumes a whole block, which is why a folder of a million tiny files wastes space. Block storage — addressing data as numbered blocks rather than as one long stream — is what makes random access possible: the drive can jump to block 47,000 without reading the 46,999 before it.

The filesystems you will actually meet

FilesystemWhereKnow this about it
NTFSWindowsPermissions (ACLs), journaling, encryption, compression, quotas. The one Windows system files live on.
FAT32Anything, ancientRead by everything, and limited: 4 GB maximum file size, 2 TB volume. The reason a big video will not fit on an old USB stick.
exFATLarge removable drivesFAT32 without the size limits, readable by Windows, macOS and Linux. The right answer for a big shared USB drive.
ext4Most LinuxJournaling, permissions, reliable, and the default on Ubuntu for years.
XFSLinux serversScales well with very large files and many parallel writes.
APFSmacOSCopy-on-write, snapshots, native encryption. Replaced HFS+.
ReFSWindows ServerIntegrity streams and resilience; not a general desktop filesystem.

Extensions, and the trap they set

The file extension — .docx, .jpg, .exe — is a hint about what the contents are and which program should open them. It is not a guarantee: rename a text file to .jpg and it is still a text file that no image viewer can open. Windows hides known extensions by default, which is how invoice.pdf.exe gets clicked. Turning extension display on is a five-second security improvement.

I/O management and drivers

The kernel handles every device, and the driver is the part that knows how.

Everything outside the CPU and RAM is I/O: disk, keyboard, display, network card, printer, USB. The kernel's I/O manager provides one consistent way for programs to talk to all of them, and hides the fact that a printer and a network card have nothing in common.

Driver
A small piece of software that knows one device's commands. The kernel routes through it. A wrong or corrupt driver is the most common cause of "the hardware is fine but the OS cannot see it".
Interrupt
How a device gets attention: it signals the CPU, which stops what it is doing and handles it. Without interrupts the CPU would have to keep asking every device whether anything happened.
Buffer
A holding area so a fast device and a slow one can work together — a print spooler is a buffer you can see.
Plug and play
The OS detects a device, identifies it, and loads a driver. Convenient, and the reason an old printer can install itself and a new one cannot.
The support rule this establishes: when a device misbehaves, the sequence is device → cable → port → driver → operating system update. Most "broken hardware" is a driver or a cable, and both are cheaper to test than a replacement.

The boot process, in six steps

The most useful diagnostic sequence in this module: each step fails in a recognisable way.

#StepIf it fails here, you see
1Power on — the PSU delivers DC, the board's power-good signal releases the CPUNothing at all: no fans, no lights. Suspect power first.
2Firmware — BIOS or UEFI initialises hardware and runs the POSTFans spin, no display, beep codes or a POST code. Suspect RAM, CPU seating, or the graphics card.
3Boot device chosen — firmware reads the boot order and finds a device"No bootable device" or an empty firmware screen. Suspect the drive, the cable, or the boot order.
4Bootloader runs — Windows Boot Manager, GRUB, or macOS's boot.efiA GRUB prompt, a Windows recovery screen, or "operating system not found". The drive is fine; the bootloader is not.
5Kernel loads and initialises memory, drivers and the filesystemA kernel panic, a blue screen very early, or a spinner that never finishes. Suspect a driver or corruption.
6User space starts — the first process starts services, then the login screenThe OS is running but the desktop never appears, or you get a login loop. Suspect a service, a profile, or a full disk.
Safe mode and its Linux equivalents exist to break the loop between steps 5 and 6: boot with a minimal set of drivers and services, and if it works, the fault is in something you just excluded. That is a diagnosis, not a fix — but it is half the work.

Dual boot is just two bootloaders (or one that lists two kernels) and two partitions. It fails in predictable ways: the boot manager lists an OS that is gone, or the firmware's Secure Boot refuses a bootloader it does not have a key for.

Logs: the machine already wrote down what happened

Every operating system keeps a record. Knowing where it is turns 'it broke' into 'this line, at this time'.

SystemWhere the logs areWhat to look for
WindowsEvent Viewer → Windows Logs (System, Application, Security)Red error entries at the time of the fault. The Event ID is the thing to search.
Linux/var/log/ — syslog, auth.log, and journalctl for the systemd journalRepeated warnings, "out of memory", failed authentication. journalctl -b -1 reads the previous boot, which is exactly what you want after a crash.
macOSConsole.app, or log show --last 1hCrash reports in Console → Crash Reports, and the unified log for everything else.
FirmwareThe board's own event log, in the firmware setupHardware errors, thermal events, and the fact that the machine restarted unexpectedly.

A log entry has four useful parts: when, what, which component, and severity. The timestamp is what turns a log into evidence — matching the moment the user says it broke to the entries around it is the whole technique.

Reading a log is a skill, not a chore. Filter by time first, then by severity, then search the error ID or message. A thousand lines of information is not noise if you only need the eleven from 14:32.

Installing an operating system

The course's Qwiklabs put you in front of Windows and Linux and make you do it. The order of operations is the same everywhere.

StepWhat you actually do
1. Check compatibilityCPU, RAM, disk space, and — on Windows 11 — TPM 2.0 and Secure Boot. Reading this first saves an hour.
2. Get the imageAn .iso from the vendor. Never from a random mirror: a modified installer is a well-known attack.
3. Make bootable mediaWrite the ISO to a USB stick with Rufus or balenaEtcher. This erases the stick.
4. Boot from itFirmware boot menu (often F12, F11 or Esc at power-on) or change the boot order.
5. Partition and formatChoose GPT (UEFI) over MBR unless the machine is genuinely old. Decide the partition layout — and know that this step is where data is destroyed.
6. Install, then updateThe installer copies files, then reboots into the OS. Then you install drivers and run updates, which is not optional.

Doing it on Linux, concretely

The course walks through Ubuntu on a Qwiklabs machine. The shell commands you are asked to use are worth knowing by hand: ls to list, pwd to see where you are, mkdir to make a folder, cd to move, touch to create an empty file, and echo $SHELL to confirm you are in bash.

Install is destructive by design. Before you touch partitions, the question is not "do I have a backup" but "have I tested that the backup restores". A backup you have never restored is a belief, not a backup.

Virtual machines: the escape from choosing

A virtual machine is a whole computer emulated in software, running on shared hardware. A hypervisor runs the VMs: type 1 sits directly on the hardware (Hyper-V, ESXi, KVM), type 2 runs as an application (VirtualBox, VMware Workstation).

This is the single most useful tool in this module. A VM lets you install an operating system, break it, and throw it away in ten minutes — which is exactly what the labs are for, without risking the machine you are sitting at. Snapshots make it better still: save the state, do the dangerous thing, roll back.

Remote access: doing it without walking over

Support at scale is remote. These are the four tools, and what each one actually gives you.

ToolPortWhat you get
SSH22An encrypted terminal on another machine. The standard for Linux and network devices. OpenSSH is the implementation you will meet; PuTTY is the Windows client the course names.
RDP3389Windows' remote desktop: you see the other machine's screen. mstsc.exe is the built-in client.
VNC5900Cross-platform remote desktop. Convenient, and not encrypted by default — tunnel it.
VPNvariesNot a remote-control tool: it puts your machine inside a private network over the internet, so the other tools can reach things that are not public.
The difference that matters in a ticket: SSH gives you a shell and almost no bandwidth; RDP gives you a desktop and a lot of bandwidth. Over a bad link, the shell works and the desktop is unusable. Choosing the cheaper tool is a support skill.

Security note, because it is the exam's favourite: exposing RDP or VNC directly to the internet is how machines get ransomwared. Remote access belongs behind a VPN, or through a gateway that authenticates first and brokers the connection.
