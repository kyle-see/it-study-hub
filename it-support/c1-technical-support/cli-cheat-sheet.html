trap <code>rm -r</code> has no single-command CMD twin. <code>rmdir /s</code> removes <em>directories</em>; hand it a file and it answers <code>The directory name is invalid.</code> The pair is <code>del /s /q</code> for the files, then <code>rmdir /s /q</code> for the folders.

trap <code>robocopy /ZB</code> fails on a standard account — exit code 16, nothing copied, <code>ERROR : You do not have the Backup and Restore Files user rights.</code> <code>/ZB</code> needs elevation. <code>/E /MT</code> needs nothing and works.

note robocopy exit codes are not errors. 0–7 means success (0 = nothing to do, 1 = files copied, 3 = copied plus extra files present). 8 and above is a failure.

note <code>xcopy src dst</code> asks a question — <em>F = file, D = directory?</em> — unless the destination ends in <code>\</code> or you pass <code>/I</code>.

note <code>-Head</code> and <code>-Tail</code> are provider dynamic parameters. They work on files in PowerShell 5.1 and 7, but <code>Get-Command Get-Content</code> will not list them, and they do not exist for the registry or certificate providers.

Piping and redirection

Text in bash and CMD, objects in PowerShell — and two operators that do not mean what they look like.

TaskLinux / macOSWindows (CMD)PowerShell

Write / overwrite output (stdout)cmd > file.txtcmd > file.txtcmd > file.txt

note Text versus objects. In bash and CMD the pipe carries plain text, so you need <code>awk</code>, <code>cut</code> or <code>findstr</code> to reach into it. In PowerShell it carries .NET objects: <code>(Get-Process | Where-Object CPU -gt 100).Name</code> needs no text parsing at all.

trap <code>2>&1</code> is a stream merge, not a file redirect. <code>cmd *> all.txt</code> writes the file; <code>cmd 2>&1</code> on its own just prints both streams to the console. On PowerShell 5.1 a native program's stderr captured through <code>*></code> lands in the file wrapped in PowerShell's <code>NativeCommandError</code> decoration; on 7.x it is clean.

note PowerShell has no <code>&lt;</code> redirection — <code>cmd < input.txt</code> is a parse error. In CMD the order is load-bearing: <code>cmd > all.txt 2>&1</code> works, <code>cmd 2>&1 > all.txt</code> does not.

What that means in practice

the error v3.1 had PowerShell has no wildcard negation. [^abc] is not “anything but a, b, c”; it is the literal set { ^, a, b, c }. [!abc] is { !, a, b, c }. Both run happily and both return the wrong files:

'5' -like '[^0-9]'                 # True  <- a digit matches the "not a digit" set
'a' -like '[^0-9]'                 # False <- a letter does not
Get-ChildItem 'file_[^0-9].txt'    # returns file_1.txt, not file_a.txt

The working form is a -not operator:

Get-ChildItem | Where-Object { $_.Name -notlike 'file_[0-9].txt' }
Get-ChildItem | Where-Object { $_.BaseName -notmatch '\d$' }

5.1 versus 7 && and || do not exist in PowerShell 5.1 — the version that ships with Windows 11. The error is explicit: The token '&&' is not a valid statement separator in this version. The 5.1-compatible form:

.\build.ps1; if ($?) { .\test.ps1 }              # the '&&' of PowerShell 5.1
.\build.ps1; if (-not $?) { .\fallback.ps1 }     # the '||' of PowerShell 5.1

“CMD sometimes” is exactly right for *. Windows file matching treats a wildcard extension as a prefix match, so dir *.txt also returns a.txtx. PowerShell's provider does not — ls *.txt correctly excludes it. (Get-ChildItem -Filter '*.txt' on PowerShell 5.1 still includes it, because -Filter goes through the older provider path; 7.x excludes it.)

Wildcards are not expanded for native programs in PowerShell. cmd /c echo *.txt prints the literal *.txt, because PowerShell hands .exe arguments through untouched.
